# Go Port Parity Ledger

The public repository includes a [snapshot of the 828 legacy test names](go-port-legacy-cases.json)
from commit `f6896fd62c4875606ed345dd1adac0cb630de0d3`. The parity verifier
compares that snapshot with this ledger and the current Go tests. If the legacy
Git history is available locally, set `ASP_LSP_LEGACY_REF` to that commit to
also verify the snapshot against the original test files and their SHA-256 hashes.

This ledger is the deletion gate for removing the legacy TypeScript/JavaScript LSP runtime. It is intentionally conservative: only cases mapped to Go tests, merged duplicates, or package-level Go equivalents are marked as covered. Remaining `missing` rows must either gain Go coverage or be reclassified with a specific rationale before deleting the legacy runtime.

## Summary

- Legacy TS/Vitest cases tracked: 828
- Go tests discovered: 2179
- `covered`: 470
- `covered-by-package`: 90
- `merged`: 268
- `missing`: 0

## Status Semantics

- `covered`: a Go test name matched the legacy case closely enough for the first pass.
- `covered-by-package`: the legacy package-level test bucket has a dedicated Go package test counterpart.
- `merged`: duplicate legacy Node stdio coverage is represented by the Go stdio source case.
- `obsolete`: intentionally removed behavior. This must include a rationale before use.
- `missing`: no accepted Go coverage yet. This blocks runtime deletion.

## Missing Buckets

- None.

## Deletion Gate Evidence

- Legacy TypeScript/JavaScript LSP runtime directories are absent: `packages/core` and `packages/language-server` are not present in the current tree.
- VS Code client TypeScript remains only as extension/webview/UI code. `apps/vscode/src/server-path.ts` resolves `bin/asp-lsp-go` for development and `server/asp-lsp-go` for VSIX bundles; it does not resolve a Node server module.
- The VSIX package test asserts that `extension/server/asp-lsp-go` is bundled and that `extension/server/node_modules/`, `extension/node_modules/`, old native/WASM server payloads, and `asp-lsp-core` are absent.
- The package test also guards against reintroducing `packages/core`, `packages/language-server`, `@asp-lsp/core`, `@asp-lsp/language-server`, `getServerModulePath`, or `serverModule` into the extension runtime path.
- Repository search excluding this ledger and generated bundles currently finds no legacy LSP runtime imports outside those package-test guard strings.
- The parity verifier enforces source-level invariants for the real TS-Go language service, JavaScript request routing, compiler diagnostics, CSS definitions/code actions, and protocol lifecycle behavior so matching test names alone cannot satisfy the deletion gate.
